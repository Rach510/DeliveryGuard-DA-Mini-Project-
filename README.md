# DeliveryGuard

**E-Commerce Delivery Delay Analytics**  
A data analytics project built on the [Olist Brazilian E-Commerce Public Dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce).

---

## What problem does this investigate?

Online shopping platforms process thousands of orders every day.
Some orders arrive on time; others arrive after the promised delivery date.

This project investigates:

- What percentage of orders arrive late?
- Which product categories have higher late-delivery rates?
- Do some sellers experience more delays than others?
- How long does delivery typically take, and how accurate are the estimates?
- Can a simple model estimate whether an order resembles historically late ones?

The goal is to **discover and communicate useful patterns in delivery data** — not to build a live logistics system or prove causes of delay.

---

## What did we find?

> - 8.11% of the 96,470 completed orders in the dataset were delivered late.
> - The category with the highest late rate was 'audio' at 12.7%.
> - Orders placed on 'Monday' had a slightly higher late rate than the weekly average.
> - The Logistic Regression achieved an F1 score of 0.129 on held-out data, compared to a majority-class baseline of 0.947.

## Setup

### 1. Python version

Python 3.10 or higher is recommended.

```bash
python --version
```

### 2. Create a virtual environment

```bash
python -m venv venv
source venv/bin/activate        # macOS / Linux
venv\Scripts\activate           # Windows
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

### 4. Download the dataset

Go to [Kaggle — Olist Brazilian E-Commerce Public Dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) and download all CSV files.

Place them in `data/raw/`:

```
data/raw/
├── olist_orders_dataset.csv
├── olist_order_items_dataset.csv
├── olist_products_dataset.csv
├── olist_sellers_dataset.csv                    ← optional but recommended
├── olist_customers_dataset.csv                  ← optional
└── product_category_name_translation.csv        ← optional (English names)
```

You only need the first three files to run the core project.

## Running the project

### Step 1 — Preprocess the data

```bash
python -m src.data_preprocessing
```

This reads the raw CSVs, cleans them, engineers delivery features, and writes:
- `data/processed/cleaned_orders.csv` — one row per delivered order
- `data/processed/item_level.csv` — one row per item (for category analysis)

### Step 2 — Explore the data (optional)

```bash
python notebooks/exploration.py
```

Produces summary statistics and saves quick charts to `notebooks/`.

### Step 3 — Launch the dashboard

```bash
streamlit run app.py
```

Open `http://localhost:8501` in your browser.

## Understanding the metrics

### `delivery_days`
Number of days from purchase timestamp to actual delivery.  
Formula: `(delivered_date − purchase_date).total_seconds() / 86400`

### `delay_days`
Days the order arrived before (negative) or after (positive) the estimated delivery date.  
Formula: `(delivered_date − estimated_date).total_seconds() / 86400`

### `is_late`
Binary label: `1` if `delay_days > 0`, otherwise `0`.

### Late rate (%)
`late_orders / total_orders × 100`  
Always reported alongside the observation count.

---

## Analytical units

The project uses two levels of analysis:

- **Order level** — one row per order. Used for overall metrics, seller analysis, and temporal trends.
- **Item level** — one row per item within each order. Used for product-category analysis. An order with five items contributes five rows; the `is_late` flag on each row reflects the parent order's outcome.

Multi-category orders are counted once per item in the category analysis. This means a single order can contribute to multiple categories. The dashboard notes this where relevant.

## Optional ML extension

The **Predict** tab trains a Logistic Regression to estimate whether an order will arrive late.

### Features used (all available at purchase time)

| Feature | Description |
|---|---|
| `purchase_month` | Month the order was placed |
| `purchase_dayofweek` | Day of the week (0 = Monday) |
| `estimated_window_days` | Seller's promised delivery window length |
| `total_price` | Total product price for the order |
| `total_freight` | Total freight cost |
| `item_count` | Number of items in the order |
| `seller_count` | Number of distinct sellers |
| `seller_historical_rate` | Seller's past late rate (computed from orders delivered before the current purchase time) |

### Features deliberately excluded (data leakage)

- `delivery_days` — reveals the outcome
- `delay_days` — reveals the outcome
- `order_delivered_customer_date` — reveals the outcome
- Future seller statistics computed on orders after the current one

### Evaluation

The model is evaluated on a **chronological held-out set** (the most recent 20% of orders), not a random split. This more closely mirrors real-world deployment.

Metrics reported: Precision, Recall, F1, ROC-AUC, and comparison against a majority-class baseline.

## Limitations

1. **Historical data only.** The Olist dataset covers a specific time period of Brazilian e-commerce. Patterns may not generalise to other markets, platforms, or time periods.

2. **Association, not causation.** A higher late-delivery rate in one product category does not mean the product category *causes* delays. Other variables (seller location, carrier, order volume) may explain the pattern.

3. **Estimated delivery dates may be padded.** Sellers may set conservative estimates to inflate their on-time statistics. High early-delivery rates could reflect padding rather than genuine operational efficiency.

4. **The ML model is retrospective.** Performance on held-out historical data does not guarantee performance in a live system with distribution shifts.

5. **Multi-category orders.** The item-level category analysis does not perfectly isolate single-category orders. This is documented in the dashboard.

6. **Minimum observation thresholds.** The category and seller analyses apply minimum observation filters. Categories or sellers with fewer records are excluded. Users can adjust these thresholds in the dashboard.

---

## Reproducing results

1. Clone the repository.
2. Follow the **Setup** steps above.
3. Download the Olist dataset from Kaggle and place CSVs in `data/raw/`.
4. Run the preprocessing script.
5. Launch the dashboard.

The preprocessing script is deterministic: given the same input CSVs, it will always produce the same output.

The ML model uses `random_state=42` in the train/test split and LogisticRegression to ensure reproducibility.
